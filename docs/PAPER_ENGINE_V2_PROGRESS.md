## Phase 6c – simulated execution — `9cc94bb`
New pure project `NiftySignal.PaperEngineV2.Execution` (references only Core + Trading.Core cost types): `StrategyRuntime` (Flat → EntryPending → Open → ExitPending → Closed | Unresolved, per strategy, fault-contained), `PaperEngine` (`IFrameProcessor`, ascending strategy id, idempotent per bar, optional `IPaperEventSink`), typed events with deterministic ids (`EntryOrderPlaced/Filled`, `EntryRejected`, `ExitRequested/Filled`, `PositionUnresolved`, `RiskBreached`, `StrategyFaulted`), closed `RejectionReason` taxonomy.
* **Causality:** a fill needs a quote available strictly after the decision (+ latency), fresh (≤ maxQuoteAgeMs), and within the order lifetime; same-instant sibling bars and the decision frame can never fill. Entry fills also need `EntriesAllowed` (blocked → order cancelled, fail closed); exits never need it.
* **Fills:** all-or-none, ask + slippage (entry), bid − slippage ≥ 0 (exit); displayed size recorded only; fees via the existing `CostModel` (schedule matched by `fees.schedule` version; no silent zero cost). Capital = virtual capital − committed premium + proceeds; lot size via `ILotSizeSource` (missing → `LotSizeViolation`).
* **Selection:** premium window inclusive; rank by proximity to the midpoint, centre distance, strike, token.
* **Exits:** discretionary, opposite signal (exit only, no reversal), stop/target/trailing (Points|Percent on bid marks; stale marks never trigger), max-hold bars, terminal at 15:00 IST with retries until the REQUIRED `ExecutionOptions.TerminalRetryUntil` (> 15:00; no default), then `PositionUnresolved`; day change closes the books (open → Unresolved); daily-loss breach blocks entries and optionally liquidates.
* **Fail closed at activation:** `FirstAfterDecision` (unsupported: frames hold one quote per token per bar) and unknown cost schedule → typed `ActivationFailure`, strategy never runs.
* **Tests:** 58 xUnit cases in `ExecutionTests` (causality incl. sibling bars/latency, staleness, selection ranking, capital/lot/risk, gating, exits, terminal/unresolved, 30-strategy isolation + permutation determinism, journal-replay ledger equality, release blockers: assembly references and banned vocabulary).
* **Full suite on the committed tree: 2525 passed, 0 failed, 0 skipped** (PostgreSQL included). No disposable databases of mine remain (only the pre-existing `niftysignal_trading_test` fixture and older volume-bar databases).
* **Limits:** in-memory only; `AsOfEligibleBarEnd` only; spread fraction uses the mid; realized-loss risk check excludes unrealized P&L; Unresolved positions are not auto-liquidated.
* No existing test was modified in this phase.

* `V2SchemaCheck.CheckAsync` (read-only; missing schema / older / newer / foreign journal schema / unreachable DB → incompatible → V2 stays CLOSED). **Not yet wired into Host start-up** (Host is production code; wiring belongs with the Host integration step).

Crash window (journal complete, last ledger rows lost) is repaired by replay (exactly the missing rows re-appended); a stored event the replay cannot reproduce is reported, never deleted.

## Phase 6e – Telegram paper-trade notifications (durable outbox) — `906b649`
New `NiftySignal.PaperEngineV2.Alerts` + additive migration `AddAlertOutbox` (table `pev2.pev2_alert_outbox`; schema version 1 → 2, the only UPDATE is the pev2 schema-version row; idempotent owner script regenerated; nothing outside `pev2` touched).
* **Opt-in:** `AlertOptions` — every class (`Opened`, `Closed`, `OrderRejected`, `PartialFill`, `ExecutionFailure`) is **OFF by default**. Mapping: `EntryFilled`→Opened, `ExitFilled`→Closed, `EntryRejected`→OrderRejected, `StrategyFaulted`/`PositionUnresolved`→ExecutionFailure. `PartialFill` exists for the contract only: V2 v1 is all-or-none, so no partial-fill event can be produced (test asserts there is no such event type). Risk-breach, order-placed and exit-requested events send nothing.
* **Outbox / dedup:** `AlertingEventSink` writes the ledger event first, then an outbox row keyed `eventId#class` (ON CONFLICT DO NOTHING) — duplicates and a restart replay enqueue nothing twice; a crash between ledger and enqueue is repaired by the replay. An outbox failure is counted and contained by the engine; strategies and the ledger event are unaffected.
* **Delivery (`AlertDispatcher`):** claim (status Sending, attempt counted, committed) → send → Sent only on an acknowledged message id; definitive refusal → retry after `retry_after` up to `MaxAttempts` then Failed; unknown outcome, thrown transport or a claim interrupted by a crash → **Uncertain, never resent automatically**; alerts older than `MaxAge` (default 15 min, by event time) → Expired, never sent (a replay cannot burst stale messages); `FOR UPDATE SKIP LOCKED`, batch ≤ 50, concurrent dispatchers never double-send. `TelegramAlertTransport` adapts the existing acknowledged `ITelegramTextSender`; error text kept out of the rows (no token URL).
* **Text:** plain, always `V2 SHADOW (paper only) | <strategy> | …` with IST time; details cut at 300 chars.
* Tests: 14 new (`AlertTests`, 11 on PostgreSQL). Existing test touched: `PostgresPersistenceTests` schema-check numbers (version 1 → 2 baseline) — my own 6d file.
* **Full suite on the committed tree: 2550 passed, 0 failed, 0 skipped** (PostgreSQL included); no disposable databases created.
* Limits: not wired into the Host/Dashboard (no dispatcher worker exists yet; nothing is ever sent today); Telegram delivery was tested only with fakes (no network, no credentials used).
