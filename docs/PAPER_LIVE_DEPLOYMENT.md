# Live paper trading — deployment, operation and rollback

**PAPER ONLY. No broker order can be placed by this path** (proved structurally by `BrokerIsolationTests`). Nothing in this document has been executed on the VM:
the branch `feature/adaptive-paper-trading-engine-v1` has been neither merged nor deployed. All steps below are for the operator.

## 1. What is deployed

| Part | Where | Effect |
|---|---|---|
| `NiftySignal.Trading.*` assemblies | Host (and the read-only parts in Dashboard) | the engine, the durable live run, the bridge |
| `AdaptiveObserverWorker` hooks | Host | four optional calls (session start, per group, per poll, session close) into `PaperLiveBridge` |
| `trading` schema | a PostgreSQL database named by `ConnectionStrings:TradingPaperLive` | the durable ledger of paper runs |
| `/paper-live` | Dashboard | read-only view |

With `Trading:PaperLive:Enabled=false` (the shipped default) the Host behaves exactly as before: the bridge returns immediately from every call and no connection to the trading database is ever opened.

## 2. Database creation and migration (manual, once; never implicit)

The application never creates, migrates or drops anything. Use a **new, empty** database (suggested name `niftysignal_trading`) on the VM PostgreSQL. Never the tick or observer databases.

1. Create the database (operator, `psql` as a superuser): `CREATE DATABASE niftysignal_trading;`
2. Review `NiftySignal.Trading.Data/Sql/trading-schema.idempotent.sql` (generated by `dotnet ef migrations script --idempotent`; creates schema `trading`, 23 tables, indexes, check constraints, the history table and the `schema_versions` row).
3. Apply it: `psql -d niftysignal_trading -f NiftySignal.Trading.Data/Sql/trading-schema.idempotent.sql` (idempotent: a second run changes nothing).
4. Verify: `SELECT * FROM trading.schema_versions;` shows `trading-engine`, schema version 1, codec `trading-codec/4`, state `trading-state/1`; `SELECT count(*) FROM information_schema.tables WHERE table_schema='trading';` is 23.
5. Grant the Host role INSERT/SELECT/UPDATE on schema `trading`; grant the Dashboard role **SELECT only**.

The Host refuses to start a run on a database whose `schema_versions` row is missing, newer or older than the code, and says so (state `Halted`).

## 3. VM-local configuration (do not commit)

`appsettings.Local.json` of the **Host**:

```json
{
  "ConnectionStrings": { "TradingPaperLive": "<connection string of niftysignal_trading>" },
  "Trading": {
    "PaperLive": {
      "Enabled": true,
      "Capital": 0,
      "BrokeragePerOrder": 0,
      "OptionTickSize": 0.05,
      "PlumbingFamily": { "Enabled": false }
    }
  }
}
```

`Capital` and `BrokeragePerOrder` are **required and have no default** (the values above are placeholders; the operator decides them; `0` is not a valid capital). With a missing value the bridge reports `Halted` with the reason and trades nothing. `OptionTickSize` is the exchange tick of the option contracts (0.05 for NSE index options) and is also required.

`appsettings.Local.json` of the **Dashboard**: `"ConnectionStrings": { "TradingPaperLive": "<same database, read-only role>" }`.

**No strategy is registered by default**: with `Enabled=true` and no strategy the state is `NoStrategies` — nothing trades and nothing is journaled. The only available family is the TEST/PLUMBING script (`PlumbingFamily.Enabled=true` with explicit `Windows`, e.g. `{ "FromBarSeq": 5, "ToBarSeq": 5, "Direction": "Long" }`, optional `TradeSlPct`, `Tp1Pct`, `Tp1Proportion`, `MaxHoldMinutes`). It claims no edge and exists to prove the plumbing; it must not be left enabled for normal operation.

## 4. Deployment procedure (when approved)

Outside market hours (a restart resets the Observer warm-up state; see CLAUDE.md): build, deploy with the existing `deploy.ps1`, verify service status, binary timestamps and `logs/niftysignal-*.log` as usual. Deploy with `Enabled=false` first and confirm the Host and Dashboard behave as before; enable PaperLive in a second step.

## 5. Pre-market checklist (each trading day)

1. Host service running; the log shows `Starting NiftySignal Host`, the expected build identity and **no** `PAPER-LIVE HALTED` line.
2. `trading` schema present and compatible (the Host logs the halt reason otherwise).
3. Configuration as intended: `Enabled`, `Capital`, `BrokeragePerOrder`, `OptionTickSize`; the plumbing family on only if a smoke test is planned.
4. Dashboard `/paper-live` loads (before the first run it says "No paper-trading run has been recorded yet").
5. Observer healthy as usual (existing checks).

## 6. 09:30 first-live-bar checklist

1. After the Observer creates today session (09:30) the log shows `Paper-live run paper-live-v1:<date>:<session> opened`.
2. `/paper-live`: the run status appears; "Last finalized bar" advances with every completed Adaptive bar; "Last commit" is recent.
3. Feed integrity `Healthy`; no problem banners; the steps / inputs counters grow.
4. With the plumbing family enabled: at its scripted bar an entry appears (open position with stop / TP1 / max-hold deadline); MFE / MAE start filling; the exits fire as configured; the closed trade shows reason, P&L and MAE / MFE.
5. Anything unexpected: set `Enabled=false` and restart (see rollback); the ledger is kept.

## 7. Restart test (before relying on it)

During a plumbing position: stop the Host service abruptly (or kill the process), start it again. Expect: log `Paper-live run ... opened (session start): replayed N steps / M inputs`; the open position reappears with the same remaining quantity, TP1 state, stop / TP1 / max-hold levels and MAE / MFE; no second entry; the state is `Live`. Bars completed while the Host was down are not replayed into the engine: the engine is told of the gap (feed degradation, then recovery) and blocks entries during its recovery period.

## 8. Rollback

* **Fast, no deployment:** set `Trading:PaperLive:Enabled=false` in the Host `appsettings.Local.json` and restart the service (outside the market window if possible). The ledger stays; an unfinished run stays unfinished and `/paper-live` flags it ("never reached its final close") once its trade date is past.
* **Code:** redeploy the previous build with `deploy.ps1`; the Observer hooks are optional and the previous build ignores the `trading` schema.
* **Data:** the `trading` schema is independent. It can be left in place or removed (`DROP SCHEMA trading CASCADE;` — destructive, operator decision only). Nothing outside the `trading` schema is ever written by this path.

## 9. Safety properties (all covered by tests)

Paper only (no broker / order / HTTP / ingestion assembly in the path; `Broker` execution and the `RealOrder` profile are refused); off by default; no strategy by default; replay and restart never create a trade; every input and every step is committed atomically with its typed rows and risk-ledger cache; ownership is fenced (a second writer cannot change the run); derived data that disagrees with the outputs halts recovery; real process kills (including inside an open transaction) converge to the uninterrupted run.

## 10. Known limits

* Option quotes of the whole option universe are journaled (every tick of every option token); the volume was not measured against a real session on this machine. Replay of a synthetic 36 865-group session takes 0.6 s; if a real day proves too heavy, the quote journaling can be narrowed without changing the model.
* Quotes and bars that were never delivered while the Host was down are not reconstructed; the engine is told of the gap.
* A run whose process was down at the final close is not finalized automatically (flagged on the Dashboard; operator decision).
* No real strategy exists yet; the rules of the first real family, its variants and their risk limits are a separate decision.
